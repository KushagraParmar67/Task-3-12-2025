1. Executive Summary

This report analyses the English-language SwiftKey corpus provided for the Johns Hopkins Data Science Capstone. The corpus contains three sources — Blogs, News articles, and Twitter posts — totalling over 557 MB, 4.27 million lines, and 102 million words. These data underpin a next-word prediction engine and an accompanying Shiny application.

Data loaded successfully. All three files were read directly from the SwiftKey corpus. Statistics are derived from the complete files; N-gram frequency analyses use a representative stratified random sample of 50,000 lines per source (150,000 lines total) to ensure computational tractability.

5. Key Findings for Management

Summary for a non-technical reader: We successfully ingested over half a billion characters of English text from three very different sources. The data is rich, varied, and sufficient to build an accurate word prediction engine.

Scale

  • The combined corpus contains 102 million words across 4.3 million documents.
  • Total raw data: 557 MB — a substantial but tractable dataset.
  • Twitter provides the most lines (2.36 M) but the shortest text; Blogs provide the richest per-document vocabulary.

Writing Style Differences

  • Twitter averages only 13 words per post — highly informal, contractions and slang (e.g., lol) are frequent.
  • Blogs average 42 words per entry — conversational but more structured.
  • News averages 34 words per article paragraph — formal, with "said" being the top content word by a wide margin.

Language Patterns

  • The top 10 words account for ~28% of all token occurrences — a classic Zipfian distribution.
  • Contractions (it's, don't, I'm) are among the most common bigrams, indicating colloquial usage dominates.
  • Trigrams like "a lot of", "one of the", and "going to be" are strong predictable phrase starters.

Data Quality Notes

  • Blogs contain extremely long lines (max 40,834 chars) suggesting some entries are full-length articles.
  • Twitter lines are hard-capped at 141 characters — the 140-char limit is clearly reflected.
  • Some cleaning will be needed: punctuation-attached tokens (s, t) from contractions, numeric tokens, and special characters.

6. Prediction Algorithm Plan

This section outlines the strategy for building an N-gram language model capable of real-time next-word prediction.

Step 1 — Text Cleaning Pipeline

StepActionRationale
1Unicode normalisation (NFC) + remove non-ASCIIEnsures consistent character encoding
2Remove URLs, email addresses, Twitter handles (@user), hashtagsNon-predictive, source-specific noise
3Remove numbers and numeric stringsLow reuse across contexts
4Expand common contractions (don't → do not)Improves N-gram coverage consistency
5Lowercase all tokensReduces vocabulary size without semantic loss
6Strip punctuation except sentence-boundary markersCleaner token boundaries
7Remove profanity via blocklistProduction-safe predictions
8Trim whitespace; drop empty linesNormalise input

Step 2 — Tokenisation & N-gram Generation

  • Sentence-boundary tokenisation using the tokenizers R package.
  • Generate unigrams (1-grams), bigrams (2-grams), trigrams (3-grams), and quadgrams (4-grams).
  • Add start-of-sentence (<s>) and end-of-sentence (</s>) boundary tokens.
  • Store N-gram tables as data frames: prefix | next_word | count | probability.
  • Apply frequency floor (drop N-grams with count < 2) to reduce memory footprint from ~5 GB to ~200 MB.

Step 3 — Stupid Backoff Language Model

Chosen approach: Stupid Backoff (Brants et al., 2007). Simple, fast, scales well — ideal for a Shiny app requiring low-latency responses.
  1. Given input phrase w₁ w₂ … wₙ, look up the 4-gram prefix wₙ₋₂ wₙ₋₁ wₙ in the quadgram table.
  2. If found: return top-k completions ranked by relative frequency.
  3. If not found: back off to trigram prefix wₙ₋₁ wₙ, applying a discount factor λ = 0.4.
  4. If still not found: back off to bigram prefix wₙ, applying λ² = 0.16.
  5. Final fallback: return top-k unigrams by corpus frequency.

Step 4 — Prediction Workflow

StageInputOutputLatency Target
Pre-processRaw user textCleaned token sequence< 5 ms
Extract prefixToken sequenceLast 1–3 tokens< 1 ms
Table lookupPrefix (4g → 3g → 2g → 1g)Candidate next-word list< 10 ms
Rank & returnCandidate list + scoresTop 3 predictions< 2 ms

7. Shiny Application Plan

User Interface Design

The application presents a clean, single-page interface with three zones:

  1. Input Panel — A large text input box where the user types freely. Prediction updates in real time after each word (≥ 200 ms debounce to avoid excessive computation).
  2. Prediction Panel — Three large clickable suggestion buttons showing the top 3 predicted next words. Clicking a button appends the word to the input.
  3. Info Panel — A collapsible section showing which N-gram level was used (4-gram / 3-gram / 2-gram / fallback), giving the user insight into prediction confidence.

Technical Architecture

Back-end (server.R)

  • Load pre-built N-gram RDS tables at startup (single load, kept in memory).
  • Expose a reactive predict_next() function.
  • Return top-3 predictions with scores within 20 ms.
  • Handle edge cases: empty input, out-of-vocabulary prefixes, single-word input.

Front-end (ui.R)

  • Built with shinydashboard or bslib for a modern look.
  • Responsive layout — works on desktop and mobile.
  • Prediction buttons styled distinctly (rank 1 = primary colour, rank 2/3 = secondary).
  • Optional: word cloud of top corpus terms for visual appeal.

# ── 1. Load data ─────────────────────────────────────────────
blogs   <- readLines("final/en_US/en_US.blogs.txt",   encoding = "UTF-8", warn = FALSE)
news    <- readLines("final/en_US/en_US.news.txt",    encoding = "UTF-8", warn = FALSE)
twitter <- readLines("final/en_US/en_US.twitter.txt", encoding = "UTF-8", warn = FALSE)

# ── 2. Summary stats ─────────────────────────────────────────
file_stats <- function(lines, name) {
  data.frame(
    Source     = name,
    Lines      = length(lines),
    Words      = sum(stringr::str_count(lines, "\\S+")),
    Characters = sum(nchar(lines)),
    AvgWords   = mean(stringr::str_count(lines, "\\S+")),
    stringsAsFactors = FALSE
  )
}
stats <- rbind(file_stats(blogs, "Blogs"), file_stats(news, "News"), file_stats(twitter, "Twitter"))

# ── 3. Sample & clean ─────────────────────────────────────────
set.seed(42)
sample_idx <- sample(seq_along(blogs), 50000)
corpus_text <- c(blogs[sample_idx], news[sample(seq_along(news), 50000)],
                 twitter[sample(seq_along(twitter), 50000)])

clean <- corpus_text |>
  tolower() |>
  stringr::str_remove_all("https?://\\S+") |>
  stringr::str_remove_all("@\\w+") |>
  stringr::str_remove_all("[^a-z\\s']") |>
  stringr::str_squish()

# ── 4. N-gram tables ─────────────────────────────────────────
library(quanteda)
corp  <- corpus(clean)
toks  <- tokens(corp, remove_punct = TRUE)
uni   <- dfm(tokens_ngrams(toks, n = 1))
bi    <- dfm(tokens_ngrams(toks, n = 2))
tri   <- dfm(tokens_ngrams(toks, n = 3))
quad  <- dfm(tokens_ngrams(toks, n = 4))

# ── 5. Stupid Backoff predictor ───────────────────────────────
predict_next <- function(input, top_k = 3, lambda = 0.4) {
  words <- tail(tolower(trimws(strsplit(input, "\\s+")[[1]])), 3)
  for (n in 4:1) {
    prefix <- paste(tail(words, n - 1), collapse = "_")
    tbl    <- get(c("quad","tri","bi","uni")[5 - n])
    hits   <- sort(colSums(tbl[, grep(paste0("^", prefix, "_"), colnames(tbl))]), decreasing = TRUE)
    if (length(hits) >= 1) {
      preds <- sub(paste0(".*_"), "", names(head(hits, top_k)))
      return(data.frame(word = preds, score = head(hits, top_k) * lambda^(4 - n)))
    }
  }
  return(data.frame(word = names(head(sort(colSums(uni), decreasing=TRUE), top_k)), score = NA))
}
